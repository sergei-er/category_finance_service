> Актуализация 26.11.2026: одноконтурное ограничение М-02 отменено. В `gost-areas-2` оценки процессов рассчитываются по группам одинакового уровня, затем объединяются по формулам (9)–(12). Общий жизненный цикл разных уровней остаётся открытым вопросом М-05. Исторические утверждения ниже о несуществующем движке относятся к датам их записи.

## Действующая модель расчётных областей (26.11.2026)

Повторно визуально проверены PDF-страницы 12–13 (печатные 8–9): формулы (6)–(13), определения величин и п. 7.8.

- Одна `CalculationArea` объединяет все выбранные контуры с одним **зафиксированным** уровнем. Формируется одна оценка меры на область, для управления — дополнительно на процесс (6.7, 6.10.2). Оценка должна описывать реализацию во всей группе. Контуры и системы не создают дополнительных голосов или весов.
- Выбор мер и четыре направления управления рассчитываются отдельно для каждого уровня. Общий организационный документ может быть свидетельством нескольких оценок, но его наличие не копирует оценку автоматически между уровнями или процессами.
- Формулы (9)–(12) объединяют именно `E_i` каждого процесса. Набор весов зависит от всех уровней зафиксированной области. Отсутствующий уровень блокирует расчёт; исключение отдельной меры не убирает уровень автоматически.
- Жизненный цикл считается по формуле (7) внутри каждой группы. Для единственного уровня его `E_AC` включается один раз в (13), даже если контуров несколько. При обоснованном отсутствии жизненного цикла знаменатель равен числу процессов. `Z` определяется по реестру фактов обследования и вычитается один раз после объединения процессов.
- Неполные ответы и решения, нулевой знаменатель и неразрешённое «Н» по-прежнему блокируют результат. Подпроцессы/направления с полностью исключённым набором не получают автоматический ноль.

### М-05 — жизненный цикл при разных уровнях защиты

В п. 7.6 определения входов и знаменателя относятся к соответствующему уровню; п. 7.8 устанавливает межуровневые коэффициенты только для процессов `E_i`; п. 7.10 использует единственное `E_AC`. В предоставленных формулах не найдено правила объединения нескольких `E_AC`.

До подтверждения такого правила приложение сохраняет групповые оценки жизненного цикла и объединённые оценки процессов, но возвращает `status=undefined`, `result=null` с причиной М-05 и запрещает утверждение. Даже равенство групповых `E_AC` не считается достаточным нормативным основанием. Усреднение, минимум, копирование весов процессов или выключение жизненного цикла ради результата не применяются. Для снятия ограничения необходим проверяемый источник/методическое решение, а не произвольный коэффициент.

Новый независимый пример: один процесс, `E_1=1`, `E_2=0,50`, `E_3=0,25`, жизненный цикл обоснованно не оценивается, `Z=1`. По (9): `0,6×1 + 0,3×0,50 + 0,1×0,25 = 0,775 → 0,78`. По (13): `R=0,78−0,01=0,77`. Три контура уровня 1 дают тот же результат группы, что один, при одинаковой подтверждённой реализации.

### Исключения, компенсации и свидетельства

Пункт 6.11 допускает определение неоцениваемых областей до выставления оценок. В тексте названы связь меры с неиспользуемой технологией и отсутствие необходимости для нейтрализации актуальных угроз по модели угроз. Во втором случае проверяется актуальность и обоснованность модели. Основания и перечень исключений входят в отчёт. Это не право исключить меру только из-за её невыполнения или отсутствия загруженного файла.

Пункт 6.12 предписывает оценивать компенсирующие меры по соответствующей шкале 6.10.1–6.10.3 и включать обоснование в отчёт. Замена меры не создаёт дополнительный голос в среднем и не является автоматическим исключением. В протоколе нужна связь исходной меры с оценённой компенсацией.

Пункты 6.13 и 6.15 рассматривают источники свидетельств шире файла: документы, опросы, наблюдения, настройки и результаты технических средств. Поэтому отсутствие файла в карточке само по себе не доказывает отсутствие свидетельств; источник и подтверждаемые факты должны документироваться. Полная реализация форм сбора свидетельств остаётся отдельной задачей.

### Нарушения и Z

Приложение Б (справочное, печатная с. 13) визуально проверено: пункты Б.1–Б.19. Полный перечень здесь не перепечатывается. Он не заменяет условия п. 7.10: учитываются самостоятельно выявленные проверяющей группой факты, допускающие инциденты с ущербом организации или клиентам. Для фактов, самостоятельно выявленных организацией, п. 7.10 устанавливает исключение из снижения при проведённом до завершения оценки разбирательстве и документированных принятых или запланированных мерах реагирования.

### Округление: норма и принятая реализация

Подтверждённая норма п. 7.11: оценки раздела 7 округляются до двух знаков по математическим правилам. Принятая пользователем 04.11.2026 интерпретация для реализации: завершать каждый именованный результат формул (1)–(13) округлением, а в зависимую формулу передавать округлённую оценку. Суммирование и умножение внутри одной формулы выполнять без дополнительного округления каждого слагаемого. В протоколе сохранять выражение до округления и округлённый результат. Этот порядок является явной интерпретацией последовательности вычислений, а не дополнительной цитатой стандарта; порядок согласован как техническое решение проекта; полноту эталонов нужно обеспечить до реализации.

Decimal со строковыми входами и ROUND_HALF_UP приняты для всех оценок, включая отрицательный итоговый R (согласование 06.11.2026). Не использовать float и не полагаться на стандартный round Python. Это техническая интерпретация математического округления: п. 7.11 не задаёт имя режима Python, а п. 7.10 не устанавливает нижнюю отсечку R.

### Синтетические контрольные примеры агрегации

Это арифметические примеры, не импортированные меры и не нормативный каталог. Они не заменяют самостоятельную таблицу шкал студента.

1. Два подпроцесса: в первом оценки [1, 0], во втором [0, 0, 0, 0, 0, 0, 0, 0]. По (1): 0,50 и 0,00. По (2): (0,50 + 0,00) / 2 = 0,25. Общее среднее десяти мер дало бы 0,10 и было бы ошибочным для этой структуры. Никаких исключений нет.
2. Проверка влияния порядка округления: оценки подпроцессов [1, 1, 0] и [0, 0]. По (1) первый результат 2/3, округлённо 0,67; второй 0,00. При принятом поэтапном порядке (2): (0,67 + 0,00) / 2 = 0,335 → 0,34. При сохранении бесконечной точности до конца получилось бы 1/3 → 0,33. Пример показывает значимость выбора порядка; значение 0,34 — эталон принятой интерпретации, не независимо установленное стандартом число.

Арифметика примеров сверена вручную; первый также проверен точными рациональными числами, округления второго — Decimal. Код расчётного ядра и unit-тесты не созданы.

Открыто до реализации: полный набор эталонов; правила О/Т/Н при формировании расчётной совокупности. При неразрешённом случае сервис должен объяснять неопределённость, а не подставлять коэффициенты.

### Согласование округления — 04.11.2026

Пользователь принял описанный поэтапный порядок. Контрольный пример: (0,67 + 0,50) / 2 = 0,585 → 0,59 при ROUND_HALF_UP. Ответ студента 0,59 верен; арифметика дополнительно проверена Decimal.

Для воспроизводимости протокол должен содержать не только показанные оценки, но также входы, знаменатели, формулу, правило округления и результат каждого шага. Для периодических дробей не требуется хранить бесконечную десятичную запись: точное выражение с числителем и знаменателем позволяет восстановить вычисление. Отображение округлённой оценки при передаче в следующую формулу другого значения противоречило бы принятому в проекте порядку. Сам по себе расчёт с неокруглёнными промежуточными значениями является другим алгоритмом, а не автоматически «не соответствующим действительности» числом.

### Жизненный цикл: неоцениваемость, ноль и неполнота

Основания: п. 6.8 (печатная с. 4) и п. 7.10, формула (13) и пояснение к ней (с. 9–10). В предоставленном тексте неоцениваемость сопровождается обозначением E_AC = 0. В модели приложения это не основание смешивать неоцениваемость с реально полученной нулевой оценкой: признак включения жизненного цикла в область хранится отдельно от его значения и обоснования решения.

| Состояние входа | Числитель до вычета нарушений | Знаменатель | Поведение |
|---|---|---|---|
| Жизненный цикл обоснованно не оценивается | Сумма E_i | T | Сохранить основание и решение; не вычислять фиктивную оценку жизненного цикла |
| Жизненный цикл оценивается, E_AC = 0 | Сумма E_i + 0 | T + 1 | Ноль участвует в среднем |
| Жизненный цикл оценивается, E_AC > 0 | Сумма E_i + E_AC | T + 1 | Оценка участвует в среднем |
| Обязательные данные жизненного цикла не заполнены или не утверждены | Не определён | Не выбирать автоматически | Результат не определён, перечислить недостающие данные |

Во всех определённых случаях после среднего вычитается 0,01 × Z, затем результат округляется согласно принятому порядку. T — число оцениваемых процессов, а не мер. Решение об области предшествует расчёту: его нельзя подбирать для повышения результата. Отсутствие ответа не является основанием неоцениваемости; нужен обоснованный выбор области по п. 6.8. Самостоятельно придумывать нормативные основания для конкретной организации сервис не должен.

Синтетические контрольные примеры: два процесса с оценками 0,80 и 0,60, Z = 0. Сначала сумма процессов равна 1,40, а не 0,70. Последнее число уже является средним и не должно повторно делиться на количество показателей.

| Пример | Выражение | Округлённый R |
|---|---|---|
| Жизненный цикл обоснованно не оценивается | 1,40 / 2 − 0,01 × 0 | 0,70 |
| Жизненный цикл оценивается и получил 0 | (1,40 + 0) / 3 − 0,01 × 0 | 0,47 |
| Жизненный цикл оценивается и получил 0,50 | (1,40 + 0,50) / 3 − 0,01 × 0 | 0,63 |

Дополнительный контроль знаменателя: при четырёх процессах и оцениваемом жизненном цикле, даже если E_AC = 0, знаменатель равен 5. Для нулевого числа включённых показателей необходима объяснимая ошибка/неопределённость, а не деление на ноль.

Эти примеры проверены отдельным временным скриптом Decimal; это проверка арифметики документации, а не тестирование реализованного расчётного ядра.

### Объединение разных уровней защиты: контрольный пример

Основание: п. 7.8, формула (11), печатная с. 9 (PDF-страница 13). Для одного процесса i получены утверждённые оценки E_1i = 0,80 и E_3i = 0,50; в область входят только уровни защиты 1 и 3.

E_i = 0,8 × 0,80 + 0,2 × 0,50 = 0,64 + 0,10 = 0,74.

Это оценка одного процесса после объединения уровней, не итоговый R. Коэффициенты 0,8 и 0,2 выбираются по набору уровней, а не по количеству контуров, мер или величине оценок. Первый индекс в E_1i/E_3i обозначает уровень защиты, i — процесс. Округление выполняется после вычисления формулы по принятому порядку.

Если уровень 2 также включён в область, но его оценка отсутствует, использовать формулу (11) вместо (9) нельзя. Требуется полный набор входов для включённых уровней; до его получения результат не определён. Отсутствующая оценка не подменяется нулём и не исключает уровень автоматически. В протоколе сохраняются набор уровней, исходные оценки с их контекстом и версиями, номер формулы, коэффициенты и результат.

Пример не решает открытый вопрос формирования общих входов для нескольких контуров одного уровня: для них нельзя придумывать дополнительное среднее без подтверждённого правила. Проверка арифметики 0,74 выполнена отдельным временным скриптом Decimal; код приложения и unit-тесты отсутствуют.

### Компенсация: принятие обоснования и оценка реализации

Контрольный пример от 05.11.2026 по п. 6.12 и шкале п. 6.10.2 ГОСТ Р 57580.2-2018: проверяющий принял обоснование замены исходной меры, но по свидетельствам установил, что компенсирующая мера реализуется не в полном объёме. Оценка полноты реализации составляет 0,5. Принятие обоснования не означает оценку 1 и не исключает исходную позицию из расчётной совокупности автоматически.

В карточке и протоколе раздельно сохраняются исходная мера, описание компенсации и её обоснование, решение по обоснованию, свидетельства реализации, числовая оценка и мотивировка проверяющего. Оценка относится к конкретному контексту исходного показателя; исходную и компенсирующую меры нельзя учитывать как две независимые выполненные позиции только из-за появления замены.

Шкала выбирается по виду показателя, а не по факту компенсации: 0,5 допустимо для полноты реализации по 6.10.2 и жизненного цикла по 6.10.3, но не для выбора меры по бинарной шкале 6.10.1. При отсутствии необходимых утверждённых сведений возвращается неопределённость, а не автоматически 0,5. Пример не устанавливает нормативное правило объединения нескольких компенсирующих мероприятий в одну оценку — такой случай требует отдельной проверки.

Проверка этого примера — сопоставление установленных обстоятельств с проверенной шкалой; арифметического вычисления в нём нет. Расчётный модуль не реализован.

### Незавершённые исключения и пустой расчётный набор

Проектная обработка неопределённости по AGENTS.md; не новая формула ГОСТ. Пункт 6.11 задаёт основания определения неоцениваемых областей, но не разрешает автоматически заменять пустое среднее нулём или единицей. Проверка ниже выполняется для конкретного процесса/подпроцесса/направления и уровня; наличие других мер в обследовании не устраняет пустой набор в отдельном узле.

| Ситуация | Что установлено | Результат проверки |
|---|---|---|
| Три меры предложены к исключению, решения ещё нет | Состав оцениваемого набора не подтверждён | «Результат не определён: не завершено рассмотрение исключений по трём мерам» |
| Все три исключения утверждены, других оцениваемых мер в узле нет | Подтверждён пустой набор; знаменатель локальной формулы равен нулю | «Результат не определён: в подпроцессе нет оцениваемых мер»; деление не выполнять |

В первом случае нельзя объявлять знаменатель нулевым только из-за предложений об исключении. Во втором не допускаются автоматические значения 0, 1 или NaN, а также молчаливое удаление узла из последующей агрегации. Допустимость исключения самого узла и способ продолжения расчёта требуют подтверждённого правила; пока оно не определено, зависимые показатели не вычисляются.

При обнаружении пустого набора также проверяются импорт, версия каталога и фильтры применимости: отсутствие строк из-за ошибки данных не равно обоснованной неоцениваемости. Протокол указывает контекст узла, идентификаторы исходных мер, решения об исключениях либо ожидаемые решения и причину остановки. Для двух ситуаций нужны отдельные отрицательные тесты при реализации ядра; сейчас это критерии будущих проверок, не выполненные unit-тесты.

### Отрицательный итоговый R — решение от 06.11.2026

По проверенной формуле (13), п. 7.10, снижение 0,01 × Z может превысить среднюю оценку до снижения. В предоставленном тексте нижняя отсечка результата не установлена. Пользователь согласовал сохранение отрицательного результата без автоматической замены нулём. Это поведение проекта по предоставленной редакции, а не утверждение об актуальных правовых требованиях.

Синтетический пример: при средней оценке до снижения 0,04 и Z = 6 получаем R = 0,04 − 0,01 × 6 = −0,02. Результат сохраняется в расчётном протоколе и показывается с пояснением «Снижение за учитываемые нарушения превышает среднюю оценку до снижения». Операция max(0, R) не применяется. Средняя оценка, количество учитываемых фактов, размер снижения и итог хранятся раздельно и остаются проверяемыми.

Таблица 1 по п. 7.9 классифицирует оценки отдельных процессов E_i, поэтому отрицательному итоговому R не назначается по ней «нулевой» или другой качественный уровень. Отрицательное число само по себе не делает вычисление неопределённым при полном наборе подтверждённых входов; неполнота и незавершённые решения проверяются отдельно. Пример не разрешает отрицательные исходные оценки мер или процессов.

В этом примере результат уже имеет два знака. Правило округления отрицательного R на границе половины шага согласовано 06.11.2026: ROUND_HALF_UP, примеры ниже. До реализации необходимо расширить полный набор эталонов. Арифметика примера проверена временным скриптом Decimal; расчётный модуль приложения не реализован.

### Округление отрицательного R — согласовано 06.11.2026

Пользователь принял единый режим ROUND_HALF_UP для положительных и отрицательных результатов: ближайшее значение с двумя знаками, при точной половине шага — от нуля. Это принятое техническое правило проекта для выполнения требования п. 7.11, а не буквальное название алгоритма из стандарта. Оно не разрешает отрицательные входные оценки мер/процессов и не вводит отсечение отрицательного итога.

| До округления | После округления |
|---|---|
| 0,025 | 0,03 |
| −0,025 | −0,03 |
| −0,024 | −0,02 |
| −0,026 | −0,03 |

Пример происхождения половинной границы внутри формулы (13): сумма семи оценок процессов равна 0,28, оценка жизненного цикла равна 0,00, Z = 6. Тогда T + 1 = 8, среднее внутри формулы равно 0,28 / 8 = 0,035, R до округления равен 0,035 − 0,06 = −0,025, после округления −0,03. Среднее внутри (13) дополнительно не округляется перед вычитанием: по принятому порядку округляется завершённый результат формулы. Это синтетический арифметический пример, не данные реального обследования.

Четыре граничных значения и выражение формулы (13) проверены временным скриптом Decimal. Тесты расчётного модуля отсутствуют, поскольку модуль ещё не реализован.

### М-04: карточки фактов и предотвращение двойного учёта — 08.11.2026

В протоколе сохраняются версии карточек и решений, список учитываемых идентификаторов, основания неучёта и связи дубликатов; Z воспроизводится из этого набора, а не из текущего изменяемого состояния справочника. После фиксации обследования изменение фактов требует нового обследования по принятому правилу истории.
