## Что необходимо сделать

Разрабатываем **локальный Django-сервис внутренней оценки** защиты информации **одной** финансовой организации. Используй закреплённые в корневом `AGENTS.md` архитектуру и образовательный режим. Код должен быть написан так, чтобы автор ВКР мог разобраться в каждом модуле и подтвердить работу тестами.

**Не трактуй эту задачу как разрешение автономно разработать весь проект.** Сегодня выполняется только этап 0; дальше переходи по моему указанию, небольшими этапами.

## Этап 0 — сейчас: изучение и проектирование, без генерации приложения

1. Проанализируй репозиторий и текущие файлы. Не удаляй и не переписывай существующие реализации; несовместимости фиксируй отдельно.
2. Зафиксируй цель и границы продукта: одна организация, внутреннее обследование, несколько контуров и циклов оценки; без tenants, внешних клиентов и официального заключения независимого аудитора.
3. Построй пользовательский сценарий и матрицу ролей для администратора, специалиста по ИБ и внутреннего проверяющего.
4. Предложи логическую ER-модель. Объясни обязательные связи: нормативный каталог → версия меры → обследование → ответ/свидетельство → подтверждение → расчёт/снимок/отчёт. Учитывай исключения, компенсирующие меры и область оценки, но не вводи десятки сущностей без необходимости.
5. Сформируй карту методики по ГОСТ Р 57580.2-2018: шкалы, уровни агрегации, исключения, влияние нарушений, правила полноты и округления. Для каждой нормы укажи точный пункт/формулу и степень проверки. Не программируй непроверенные правила.
6. Предложи структуру Django-приложений и диаграмму потоков: браузер → Nginx → Gunicorn → Django (views/forms/services/templates) → ORM → PostgreSQL; отдельно приватное файловое хранилище и Python-расчётное ядро.
7. Составь последовательность функциональных срезов и проверяемые критерии их завершения; отрази основные угрозы и способы тестирования доступа.
8. Сохрани результаты в `docs/REQUIREMENTS.md`, `docs/ARCHITECTURE.md`, `docs/DATA_MODEL.md`, `docs/METHODOLOGY.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/PERMISSIONS.md`, `docs/SOURCE_GAPS.md`, `docs/DECISIONS.md`, `docs/LEARNING_LOG.md`. При необходимости можно создать каркас README. **Не создавай в рамках этапа 0 Django-проект, контейнеры или код приложения.**
9. В конце объясни мне архитектуру и предложи мини-задачу: самостоятельно нарисовать или исправить часть ER-модели (например, связь обследований с ответами и свидетельствами), с критериями проверки.

## Последующие учебные этапы (план, а не разрешение на немедленную реализацию)

### Этап 1. Каркас Django

Python 3.12, Django 5.2 LTS, PostgreSQL 16, настройка settings, простая страница из Django Templates, Nginx/Gunicorn и Compose. Миграции, `.env.example`, тесты запуска. Урок: как проходит HTTP-запрос через Nginx/Gunicorn/Django, что такое MVT, settings и миграции. Самостоятельная задача: создать view и template для страницы «О сервисе» или написать тест для существующего view. Не приступать к этапу 2 автоматически.

### Этап 2. Пользователи, роли, единый профиль организации

Встроенный Django auth, группы и permissions, админское создание пользователей, отсутствие публичной регистрации, ровно один профиль. Урок: серверные сессии, CSRF, RBAC, Django Forms и модель данных. Самостоятельная задача: добавить permission-тест на запрещённую операцию.

### Этап 3. Версионированный справочник ГОСТ

Структура процесса/подпроцесса/направления/меры, применимость и проверяемый импорт только подтверждённых записей. Урок: Django ORM, нормализация БД, фикстуры, миграции и валидация справочника. Задача студента: реализовать фильтр мер по разделу и тест на него.

### Этап 4. Обследования и анкеты

Область оценки, контуры, выбор применимых мер и снимок версии каталога; хранение черновых ответов и рабочих статусов, отличных от оценки. Урок: модели связей, Django Form/ModelForm, транзакции. Задача студента: добавить проверку недопустимого состояния или тест сохранения ответа.

### Этап 5. Свидетельства и внутреннее согласование

Закрытое файловое хранилище, права на чтение/скачивание, загрузка и журнал; отдельные решения по исключениям и компенсирующим мерам. Урок: файловая безопасность, IDOR, CSRF, lifecycle данных. Задача студента: написать отрицательный security-тест на доступ неавторизованного пользователя к файлу.

### Этап 6. Расчётное ядро

Чистые Python-функции с Decimal, точная последовательность формул по ГОСТ Р 57580.2-2018, протокол вычислений, отказ от расчёта при неполноте. Урок: декомпозиция, численная точность, тестирование по эталонным вручную рассчитанным примерам. Задача студента: самостоятельно посчитать один тестовый случай и написать тест. При отсутствии проверенной методики этот этап блокируется.

### Этап 7. Результаты, сравнение и отчёт

Серверные страницы результатов, предварительная визуализация, проект отчёта и приложения, экспорт из неизменяемого снимка. Урок: Django Templates, генерация документов, версионирование. Задача студента: создать тест на воспроизводимость отчёта или добавить поле в шаблон.

### Этап 8. Финальные испытания и демонстрация

Полный путь на синтетической организации: вход → обследование → анкета → свидетельства → согласование → расчёт → отчёт → повторный просмотр. Security-тесты, журналирование, резервное копирование/восстановление, проверка Docker Compose, исправление замечаний. Подготовить `docs/DEMO_SCRIPT.md` и материал для практической главы ВКР. Урок: измеримая приемка системы и защита архитектурных решений.

## Обязательные правила для всех этапов

- Перед кодом коротко объясни концепцию и **предложи мини-задачу пользователю**. Выбери небольшой объём, который не тормозит разработку, но требует самостоятельного участия.
- После реализации покажи изменённые файлы и цепочку работы компонента, команду проверки и её **фактический** результат. Сформулируй 2–3 контрольных вопроса по модулю.
- Не исправляй самостоятельно часть, которую пользователь решил выполнить, пока он не попросит «покажи решение».
- Не скрывай неопределённость: если файл, нормативная формула или зависимость недоступны, обозначь пробел и не выдавай предположение за законченную реализацию.
- Не сканируй банковскую инфраструктуру; не подключай реальные данные и внешние API без отдельного разрешения.
- Переключение этапов по команде пользователя. Внутри согласованного этапа можешь самостоятельно исправлять ошибки и запускать тесты.
